以下是检查日志的发现和建议

 

 

日志发现：

1.  在UTC时间11月12日 4:21 (北京时间12:21) 分发现HBA4 (推测此时为主active链路)上fc frame没有得到回应，超时后触发链路枚举
2.  然后ESXi通过HBA3枚举链路得到返回的device 位 标志 0x2,  scsi sense data 6/29/0， 为存储设备忙，之后一直到超时触发all path down记录生成。

 

 

总结：

1.  未发现lpfc driver error，只是从日志看，问题时间段疑似FC 链路有frame dropping或者盘柜未及时响应FCP CMD，(注，此状态并非是说存储有问题，具体情况需以存储的日志记录为准)
2.  未发现ESXi异常，此问题只是FC链路状态异常导致
3.  未发现明确硬件异常，初步判断所有硬件正常。

 

 

建议：

1.  检查发现该ESXi主机的LPFC驱动和FC卡固件版本不匹配ESXi版本，但是建议优先考虑外置盘柜是否兼容下面所附的目标版本，如果兼容，那么推荐更新到该版本观察.  （因log中未发现lpfc driver 本身的错误，故此建议非主要因素，是因为兼容性问题推荐考虑）
2.  因从日志检查发现链路不稳定初始触发是因为FC Frame timeout，之后枚举链路时存储设备一直报告 check condition状态，如果此时其他挂载同一存储同一Lun的ESXi主机读写该Lun正常，那么问题多数会跟FC链路和最佳实践(Best practice)是否得以完全执行有关系，
3.  推荐根据厂商的对应存储的最佳实践(Best practice guide )来检查并调整，包括以下项目：
    a.  FC HBA是否被存储设备所兼容
    b.  FC HBA 固件/驱动是否符合存储设备运行需求
    c.  链路连接方式，拓扑结构是否符合最佳实践并且已应用
    d.  FC HBA command timeout参数，queue参数是否有厂商推荐参数并且已应用
    e.  FC HBA的多链路模式，多链路管理软件是否有厂商推荐参数并且已应用
    f.  LUN的划分和分配是否符合虚拟机应用需求，一般不推荐在少数的LUN上堆积太多VM，
    g.  是否存在特定的多链路的附加参数需要根据该盘柜进行调整，请检查存储厂商的best practice 手册
4.  当前外置存储的两个LUN均工作在VMFS-5模式，如果该两个LUN都是被ESXI6.7 挂载，没有更低版本的ESXi主机连接并使用该两个LUN,  推荐在有维护窗口的时候将其升级到VMFS6
